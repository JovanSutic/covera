# Phase 3 — the guest surfaces read the type

**Prerequisite:** phase 2, and a checkout of `covera-hono` at `../covera-hono` (steps 3.1–3.4 run
there). Supersedes D2 — see D23.
**Gate:** two gates. Steps 3.1–3.4 run `npm run gate` **in `covera-hono`**; steps 3.5–3.8 run
`npm run gate` **in `covera`**. Each step states which.

---

## Why this phase needs the backend

Phase 1 established the rule: on every surface an asset's displayed identity is
`asset.asset_type.code`, with the category read off the same object (D1). Two files never got that
treatment, because their payloads cannot support it:

| File | Line | Reads today |
| --- | --- | --- |
| `src/components/guest/RoomPhotoItem.tsx` | 85 | `asset.name` |
| `src/components/forms/FlagContentForm.tsx` | 179 | `asset.name` |
| `src/components/forms/FlagContentForm.tsx` | 180 | `asset.category` |

Both take `ShotWithAssets`. `ShotWithAssets.assets` and `InspectionFlag.assets` are **inline**
objects in `src/api/generated/requests/types.gen.ts` that carry `assetTypeId` but **no**
`asset_type` — unlike `Asset`, which does. They are inline because the backend builds them from
`SelectAssetSchema` (`covera-hono/src/modules/inspections/inspections.schema.ts`,
`inspectionFlags.schema.ts`) rather than the named `Asset` schema.

So `asset.asset_type.code` in these two files is a type error today, and no amount of frontend work
fixes it: the guest reaches `/inspection/:id` with no session, and `GET /assets/types` is
`authGuard` + `rolesGuard(["admin","host"])` (`covera-hono/src/modules/assets/assets.contract.ts`),
so the catalogue cannot be fetched to resolve `assetTypeId` client-side. The payload has to carry
the type. Steps 3.1–3.4 make it do so.

---

## ⚠️ Deploy ordering — read before shipping

The frontend reads `asset.asset_type.code` with **no fallback** (D1). Against a backend that does
not return `asset_type`, `asset.asset_type` is `undefined` and `/inspection/:id` throws
`Cannot read properties of undefined (reading 'code')` — the guest walkthrough stops rendering.

**`covera-hono` must be deployed to `covera-api.josutic-sutic.workers.dev` before the `covera`
branch merges.** Step 3.5 regenerates the client against a *local* server (D25), which deliberately
removes the deploy from the middle of this phase — it does **not** remove it from the release
order. See D26.

### Step 3.2 — Point both guest payloads at the named `Asset` schema

**Touch.** `../covera-hono/src/modules/inspections/inspections.schema.ts` (edit),
`../covera-hono/src/modules/inspections/inspectionFlags.schema.ts` (edit)

**Do.** In **both** files, drop `SelectAssetSchema` from the `@/db` import and add an import of the
module schema that already wraps an asset with its type:

```ts
import { AssetSchema } from "../assets/assets.schema";
```

In `inspections.schema.ts` place it as the last import line, after
`import { ApartmentSchema } from "../apartments/apartments.schema";`. In
`inspectionFlags.schema.ts` place it directly after the `} from "@/db";` block.

Then change the two `assets` fields:

| File | From | To |
| --- | --- | --- |
| `inspections.schema.ts` | `assets: z.array(SelectAssetSchema),` | `assets: z.array(AssetSchema),` |
| `inspectionFlags.schema.ts` | `assets: z.array(SelectAssetSchema).default([]),` | `assets: z.array(AssetSchema).default([]),` |

`AssetSchema` is `SelectAssetSchema.extend({ asset_type: AssetTypeSchema }).openapi("Asset")` —

guest payloads stop describing their own copy of an asset and reference the same named component,

else about these two schemas changes: the flat `name` / `category` fields stay (D27).

### Step 3.3 — Attach the catalogue row in the detailed inspection payload

**Touch.** `../covera-hono/src/modules/inspections/inspections.service.ts` (edit)

**Do.** Three edits inside `getById`'s detailed branch, plus one module-level helper.

(a) Insert this directly after the import block, before `export const inspectionsService = {`:

```ts
/**
 * The relational query loads the catalogue row as `assetType`; the API contract names it
 * `asset_type`. Same rename `assetsService` performs for the host payload.
 */
const toAssetWithType = (asset: any) => {
  const { assetType, ...rest } = asset;
  return { ...rest, asset_type: assetType };
};
```

(b) In the `with:` clause, replace both occurrences of `asset: true,` with:

```ts
                asset: { with: { assetType: true } },
```

There are exactly two — one under `flags.with.flagAssets.with`, one under
`reservation.with.apartment.with.shots.with.shotAssets.with`. The second sits deeper; keep its
surrounding indentation as-is and reindent only if the linter objects.

(c) Replace the two asset mappers:

```ts
        assets: flagAssets.map(({ asset }) => toAssetWithType(asset)),
```

```ts
        assets: shotAssets.map((pivot) => toAssetWithType(pivot.asset)),
```

The first replaces `assets: flagAssets.map((fa) => fa.asset),` and the second replaces
`assets: shotAssets.map((pivot) => pivot.asset),`.

**Accept.** `npm run gate` → **GATE PASSED**. Plus
`grep -c "toAssetWithType" src/modules/inspections/inspections.service.ts` → `3` (one definition,
two call sites), and
`grep -c "asset: { with: { assetType: true } }" src/modules/inspections/inspections.service.ts` → `2`.

**Verify.** `npm run gate`

`dotenv -e .env` does not override an already-set variable, so the shell value wins. If it does not
— the Accept below fails loudly rather than silently regenerating from the worker — fall back to
editing `VITE_API_DOCS_URL` in `.env` for the duration of this step and reverting it afterwards.

**Accept.** Both guest payloads now expose the named `Asset` type:

```bash
node -e '
const s = require("fs").readFileSync("src/api/generated/requests/types.gen.ts", "utf8");
const blk = (n) => {
  const a = s.indexOf("export type " + n + " = {");
  if (a < 0) throw new Error("block not found: " + n);
  const b = s.indexOf("\n};", a);
  if (b < 0) throw new Error("block end not found: " + n);
  return s.slice(a, b);
};
const ok = (b) => b.includes("assets: Array<Asset>") || b.includes("asset_type: AssetType");
console.log("ShotWithAssets:", ok(blk("ShotWithAssets")), "InspectionFlag:", ok(blk("InspectionFlag")));
'
```

→ `ShotWithAssets: true InspectionFlag: true`

Measured on the pre-regeneration tree this prints `false false` **and still finds both blocks** — the
`throw` is what makes that `false` mean "the payload lacks the type" rather than "the extractor
matched nothing". Do not rewrite this as a `new RegExp` one-liner: the backslashes survive the shell
differently at each quoting level, and a silently non-matching pattern prints exactly the same
`false false` as a correct negative. The check accepts either shape because openapi-ts may emit a
`$ref` (`assets: Array<Asset>`) or inline the object (`asset_type: AssetType`).

Plus `npm run gate` → exit 0 with the same `Tests  4 passed (4)` as phase 2. The tree stays green
here: `asset.name` and `asset.category` still exist on `Asset`, so steps 3.6–3.7 are not what make
it compile.
