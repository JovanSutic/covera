# p7 — Guest read access to the guide (prep 5 + the Feature)

**Prerequisite:** p4, p5
**Gate:** `npm run gate`

## Why this phase exists

The Feature section's whole point: a host appoints someone — a photographer, a cleaner — who
has **no account**, and sends them a link. They open the inspection guide and do the work.

**What the backend actually allows, probed 2026-11-23:**

| Endpoint | `?accessId=` |
| -------- | ------------ |
| `GET /apartments/{id}` | ✅ |
| `GET /apartment-shots/apartment/{apartmentId}` | ✅ |
| `GET /inspections/reservation/{reservationId}` | ✅ |
| `GET /reservations/{id}` | ✅ |
| `GET /reservations/{id}/photos` | ✅ |
| `POST /inspections` | ✅ |
| `POST /apartments/{id}/photos/upload-tokens` | ❌ |
| `POST /apartments/{id}/photos/confirm` | ❌ |
| `PATCH /reservations/{id}` | ❌ |

So a guest can **read** the guide's data but **cannot submit** the proofs — the submit path is
three calls that all reject access. This phase therefore delivers the guest **read** surface
and is explicit about the rest (D38, D39).

## Step 7.1 — Access-aware fetchers

**Touch:** `src/lib/api/specialAccess.ts` (edit)

**Do:**
Add three fetchers that send `?accessId=` and use `publicApi()` — **never** `withAuth()`
(D37, invariant 8). Append to the module:

```ts
import { publicApi } from "@/lib/api/api";
import {
  getApartmentShotsApartmentByApartmentId,
  getReservationsById,
  getReservationsByIdPhotos,
} from "@/api/generated/requests/sdk.gen";

/**
 * D36/D37: the guest's reads. Each takes the `accessId` and sends it as the query parameter
 * the backend reads (verified 2026-11-23).
 *
 * These use `publicApi()` and NEVER `withAuth()`. `withAuth()` reads the Supabase session and
 * sends `Authorization: Bearer undefined` for a caller with no account, which turns a working
 * anonymous read into a 401 — the exact failure `fieldIncident.ts` and `queries/inspection.ts`
 * document for the other anonymous surfaces (invariant 8).
 *
 * The generated endpoint types pin `query?: never`, so the accessId needs the `as never` cast.
 * A `url:` override does NOT compile (TS2353) — verified by trial-compiling both.
 */
const accessQuery = (accessId: string) => ({ accessId }) as never;

export async function fetchReservationWithAccess(
  reservationId: string,
  accessId: string,
  signal?: AbortSignal,
) {
  const response = await getReservationsById({
    ...publicApi(signal ? { signal } : {}),
    path: { id: reservationId },
    query: accessQuery(accessId),
  });

  return response.data;
}

export async function fetchShotsWithAccess(
  apartmentId: string,
  accessId: string,
  signal?: AbortSignal,
) {
  const response = await getApartmentShotsApartmentByApartmentId({
    ...publicApi(signal ? { signal } : {}),
    path: { apartmentId },
    query: accessQuery(accessId),
  });

  return response.data;
}

export async function fetchReservationPhotosWithAccess(
  reservationId: string,
  accessId: string,
  signal?: AbortSignal,
) {
  const response = await getReservationsByIdPhotos({
    ...publicApi(signal ? { signal } : {}),
    path: { id: reservationId },
    query: accessQuery(accessId),
  });

  return response.data;
}
```

Merge the new imports into the file's existing import block rather than adding a second one
from the same module.

**Accept:**
- `grep -c "publicApi" src/lib/api/specialAccess.ts` → at least `3` ✓
- `grep -c "withAuth" src/lib/api/specialAccess.ts` → still `2` (the two writes only — the fetchers must not add one) ✓
- `grep -c "export async function" src/lib/api/specialAccess.ts` → `5` ✓
- `npx tsc -b` clean ✓

## Step 7.2 — Add the guest query hooks **inside the page**

**Touch:** `src/pages/InspectionGuidePage.tsx` (edit — the hooks go here, in step 7.3's file)

**Do:**
Do **not** create a new query module. The three access-aware reads are `useQuery` calls
defined **locally inside `InspectionGuidePage.tsx`**, for a structural reason:

`src/lib/api/queries/manifest.ts` walks every module in its `MODULES` map and **throws at load**
if a `use…` export does not resolve to a resource registered in `QUERY_RESOURCES` — and these
hooks cannot be registered, because a `ResourceDefinition`'s key is computed from route params
and cannot see a query parameter. Adding the module would break `manifest.ts` at import time.

Defining them in the page sidesteps this entirely: a page is not a query module, so nothing
inspects its hook names, and `prefetchCoverage.test.ts` only compares a page's imports **from
registered modules** — a locally-defined hook is invisible to it.

**The three hooks, in the page:**

```ts
function useReservationWithAccess(reservationId: string | undefined, accessId: string | null) {
  return useQuery({
    // The accessId is IN the key: two different links must not read each other's cache, and
    // neither may share an entry with the authed `reservationQueryKey`.
    queryKey: [...QUERY_ACTIONS.RESERVATIONS_GET_ID, "access", accessId ?? "", reservationId ?? ""],
    queryFn: ({ signal }) => fetchReservationWithAccess(reservationId!, accessId!, signal),
    enabled: Boolean(reservationId) && Boolean(accessId),
    staleTime: PREFETCH_STALE_TIME_MS,
  });
}

function useShotsWithAccess(apartmentId: string | undefined, accessId: string | null) {
  return useQuery({
    queryKey: [...QUERY_ACTIONS.APARTMENT_SHOTS_GET_BY_APARTMENT, "access", accessId ?? "", apartmentId ?? ""],
    queryFn: ({ signal }) => fetchShotsWithAccess(apartmentId!, accessId!, signal),
    enabled: Boolean(apartmentId) && Boolean(accessId),
    staleTime: PREFETCH_STALE_TIME_MS,
  });
}

function useReservationPhotosWithAccess(reservationId: string | undefined, accessId: string | null) {
  return useQuery({
    queryKey: [...QUERY_ACTIONS.RESERVATIONS_GET_PHOTOS, "access", accessId ?? "", reservationId ?? ""],
    queryFn: ({ signal }) => fetchReservationPhotosWithAccess(reservationId!, accessId!, signal),
    enabled: Boolean(reservationId) && Boolean(accessId),
    staleTime: PREFETCH_STALE_TIME_MS,
  });
}
```

Imports the page needs for these: `useQuery` from `@tanstack/react-query`, `QUERY_ACTIONS`
from `@/lib/api/queryKeys`, `PREFETCH_STALE_TIME_MS` from `@/lib/api/queries/shared`, and the
three fetchers from `@/lib/api/specialAccess`.

Every key is built from `QUERY_ACTIONS` (invariant 4) — the `"access"` literal is a
discriminator segment, not a resource name, so it does not bypass the registry.

**Accept:**
- `grep -c "useQuery" src/pages/InspectionGuidePage.tsx` → at least `3` ✓
- `grep -n "QUERY_ACTIONS" src/pages/InspectionGuidePage.tsx` → at least three hits ✓
- `ls src/lib/api/queries/guestGuide.ts` → does not exist ✓
- `npx vitest run src/lib/api/queries/registry.test.ts` → passes ✓
- `npx tsc -b` clean ✓

**Verify:** `npm run gate`

## Step 7.3 — Make the guide reachable by a link

**Touch:** `src/lib/router/paths.ts` (edit), `src/lib/router/routes/public.ts` (edit), `src/pages/InspectionGuidePage.tsx` (edit)

**Do:**

**(a) `paths.ts`** — change `inspectionGuide`'s `requires` from `["canOpenHost"]` to
`["public"]`:

```ts
  // D38 (feature/54): `public`, not `canOpenHost`. A host-appointed photographer holding an
  // access link has no account, so a `canOpenHost` route could only ever refuse them. The
  // page enforces "host session OR accessId" itself (D26) — a rule name cannot express a
  // query parameter, which is exactly what routes/public.ts already documents for this route.
  inspectionGuide: {
    pattern: "/inspection-guide/:apartmentId/:reservationId",
    requires: ["public"],
    params: { apartmentId: "uuid", reservationId: "uuid" },
  },
```

**(b) `routes/public.ts`** — change the route's `requires` to `"public"` to match. The rule
must be identical to the `appPaths` declaration or `tree.test.ts` fails:

```ts
    requires: "public",
```

Leave the route where it is (top-level in `appRoutes`) and leave its `data` declarations
alone — they stay valid. **A known consequence, accepted:** the route's `data` entries now
prefetch the **authed** `reservation` and `shots` for an anonymous guest too, because
`resolveResource` builds them through the registered (authed) definitions and cannot see the
accessId. A guest therefore makes two requests that 401 before the access-aware reads land.
They are inert — a failed prefetch is swallowed by `prefetchQuietly` and the page's own
access-aware hooks are what it renders from — so this is a wasted request, not a broken screen.
Changing the declarations to `params: () => null` was rejected: `prefetchCoverage.test.ts`
credits a page's **imported** hooks, and the host path's imports are unchanged, so nulling them
would break the coverage check for the host. Recorded as a noticed item in the PR.

**(c) `InspectionGuidePage.tsx`** — branch on whether an `accessId` is present.

- Read it: `const [searchParams] = useSearchParams();` then
  `const accessId = searchParams.get("accessId");`
- **Host branch** (`accessId === null`): unchanged. It keeps the existing authed reads
  (`useReservation`, `useShots`), the `getProofWindowState` gate, the submit control and the
  `submitInspectionPhotos` mutation. Do not touch this path — the host must keep the ability to
  submit.
- **Guest branch** (`accessId !== null`): use the three access-aware reads from step 7.2
  instead, and render the guide **read-only**:
  - the reservation, the shots, the before photos;
  - **no** submit control and **no** `submitInspectionPhotos` call (D38 — the three submit
    endpoints reject access);
  - the new `inspectionGuidePage.guest.readOnly` line (D39) telling the reader that the host
    completes the submission.

**A guest must never call `withAuth()`.** Concretely: `submitPhotoProofs.ts` calls `withAuth()`
and the `PATCH /reservations/{id}` inside it — a guest branch that reached the mutation would
send `Bearer undefined` and fail. Gate the mutation behind `accessId === null`.

**t() keys it renders — new:** `inspectionGuidePage.guest.readOnly`. Everything else the guest
branch shows reuses the page's existing keys.

**Accept:**
- `grep -n "requires: \[\"public\"\]" src/lib/router/paths.ts` → one hit, in `inspectionGuide` ✓
- `grep -n "accessId" src/pages/InspectionGuidePage.tsx` → at least two hits ✓
- `grep -n "useSearchParams" src/pages/InspectionGuidePage.tsx` → one hit ✓
- `grep -n "submitMutation" src/pages/InspectionGuidePage.tsx` → the mutation exists and is not reachable from the guest branch (read the diff to confirm) ✓
- `npx vitest run src/lib/router/__checks__/tree.test.ts src/lib/router/__checks__/prefetchCoverage.test.ts` → passes ✓
- `npx tsc -b` clean ✓

**Verify:** `npm run gate`

## Phase invariants

- **Invariant 8 is this phase's central risk.** Verify explicitly:
  `grep -n "withAuth" src/lib/api/specialAccess.ts` shows only the two writes, and the guest
  branch in `InspectionGuidePage.tsx` reaches neither `submitInspectionPhotos` nor any
  `withAuth()`-backed hook.
- Invariant 2: the new key exists in all four locales (step 7.4's Accept dumps all four).
- Invariant 3: the route moved rule, not location.
- `tree.test.ts` passes: `appPaths.inspectionGuide.requires` now equals the route's inherited
  rules (`["public"]`).
- The **host** path is unchanged: `grep -n "canOpenHost" src/lib/router/paths.ts` no longer
  lists `inspectionGuide`, but the page still serves a host exactly as before.

## Test rule

Steps 7.1–7.3 are wiring over tested helpers and generated calls; the one piece of genuine
logic (`absoluteUrl`, `guidePoints`) was tested in p2 and p3. Recorded as D41's opt-out. The
route-rule change is asserted by `tree.test.ts`, and the fetchers' `publicApi()`-not-`withAuth()`
rule is asserted by the greps above.

## What this phase deliberately does not do

- No guest **submission** — the three submit endpoints reject access (probed). Adding it would
  ship a button that cannot work.
- No guest access to `/incident/:incidentId/proofs` — no incident endpoint accepts access
  (p5's D31 covers the refusal state).
- No `damage_evidence` links (D18).
- No workaround for the `500`-instead-of-`403` defect: the guest refusal copy reports the
  backend's own message rather than asserting the link is invalid (D45).
