# Incident claims — decisions

Every choice the executor would otherwise make mid-flight. Approve the table in one pass, or edit it

## A. Shape and routes

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D1 | The feature is **two surfaces**, not one: a host **claim page** and a zero-auth **field portal**. | The prep doc settles this itself: "this collection of the damage photo proofs can be done by host or a cleaner, so it needs to be on a different page, so we can later grant some cleaner access to that page". One page cannot be both behind `canOpenHost` and reachable with no session. | APPROVED |
| D2 | The host **claim page is a separate page**, not a section of the reservation page. | The operator's own lean, and the deciding reason is customer education: the guidance copy ("where to do what in the Airbnb system") is long, and burying it in a section of the reservation page makes it unreadable. The reservation page keeps only a compact status section that links here. | APPROVED |
| D3 | Claim page route: `/host/apartments/:id/reservations/:reservationId/incident`, a **third sibling** under the `host` section — not a child of the reservation route. | Same reason as the existing reservation route's own comment: a child route renders into its parent's `<Outlet />`, and `IndividualApartment.tsx` has no `<Outlet />` — nesting produces a blank screen that still passes every gate check. A sibling with the full pattern written out avoids that class of bug entirely, and inherits `canOpenHost` + the section's `apartmentsHost` prefetch. | APPROVED |
| D4 | Field portal route: `/field/incident/:token`, in **`outsideRoutes`**, `requires: "public"`. | Blueprint View B requires "completely isolated views lacking navigation panels". `outsideRoutes` is the tree that exists for exactly that: a page with no session and no shell (it holds `login` and `update-password`, the latter reached from an emailed link before a session exists — the same shape as this). Putting it in `appRoutes` would render the app `Header`, its nav links and its language switcher over a page whose whole design premise is that it has none. | APPROVED |
| D5 | `appPaths` gains exactly two entries: `incidentClaim` and `fieldIncident`. | `tree.test.ts` requires every `appPaths` entry to match a built route by pattern, inherited rules and param keys — two new routes means exactly two new entries, no more (no path for a page that does not exist). | APPROVED |
| D6 | The token param is a **new `"hex32"` `ParamType`**, not the existing `"name"`. | The token is a 32-character hex string (stripped UUID). `"name"` is `/^[\w.-]+$/`, which accepts `not-a-token` and would let a garbage URL reach the API and render a *network* failure indistinguishable from the designed `FIELD_TOKEN_INVALID` state. A typed param makes the router reject a malformed token the same way `inspection/:id` rejects a malformed uuid — the split the app already makes. | APPROVED |
| D7 | Component directories: host components in `src/components/host/incident/`, field components in `src/components/field/`, pages `src/pages/host/IncidentPage.tsx` and `src/pages/FieldIncidentPage.tsx`. | Matches the existing `src/components/host/guide/` grouping — the incident flow has enough of its own parts to warrant a directory rather than crowding `src/components/host/`. | APPROVED |

The names mirror `RESERVATIONS_GET_BY_APARTMENT` / `RESERVATIONS_GET_ID`, which is the same list/detail pair. | APPROVED |
| D9 | Three new query modules: `queries/incidents.ts` (`useIncidents` / `incidentsResource`), `queries/incident.ts` (`useIncident` / `incidentResource`), `queries/fieldIngest.ts` (`useFieldIngest` / `fieldIngestResource`). | `manifest.ts` pairs a hook name to a resource **by object identity at import** and names the module basename: `useIncidents` must resolve to resource `incidents`, defined in `incidents.ts`. Splitting list from detail into two modules is not cosmetic — one module cannot own two resources' names under that rule. | APPROVED |
| D10 | `useIncidents` sends `query: { apartmentId, page: 1, limit: 100, sortBy: "createdAt", order: "desc" }` and keys on `[...INCIDENTS_GET_BY_APARTMENT, apartmentId, page, limit]`. | `GetIncidentsData.query.apartmentId` is **required** — there is no way to ask for a list without an apartment. The composite key keeps the page and limit in the identity so a second caller with different paging cannot collide with this one. | APPROVED |
| D11 | Both host surfaces resolve "the incident for this reservation" by reading the apartment's list and matching `reservationId`, via one helper `findIncidentForReservation(incidents, reservationId)`. | **No incident-by-reservation endpoint exists.** `getIncidents` is the only read that can find it. One helper, so the section and the page cannot match differently. | APPROVED |
| D12 | The field module makes **no `withAuth()` call**, in the module or in the page. | The cleaner has no session; `withAuth()` would attach `Bearer undefined`. Mirrors `queries/inspection.ts`'s existing comment for the same reason. | APPROVED |
| D13 | Writes are plain mutation functions collected in **`src/lib/api/incidentClaims.ts`**, not resources, and are never declared in a route's `data:`. | A prefetch is speculative; prefetching a write is meaningless, and `ResourceDefinition` has no shape for one. `src/lib/api/submitPhotoProofs.ts` is the existing precedent: a write module sitting flat in `src/lib/api/`, beside `api.ts` and the `queries/` directory rather than inside it. There is no `src/lib/api/mutations/` directory in this repo and this feature does not create one. | APPROVED |
| D14 | `useIncidents` requests at most `limit: 100` and the UI reads **page 1 only**. | Paging the incident list is out of scope, and the sort is `createdAt desc` so the newest claims — the ones a host is acting on — are always on page 1. **Known gap, recorded in the spec's Out of scope:** an apartment with more than 100 incidents could hide an older one from this surface. | APPROVED |

## C. Behaviour, statuses and the blueprint matrix

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D15 | The blueprint's 5-row matrix maps onto the **real** backend states, and three of its rows are not reachable. `escalated_to_aircover`, `resolved`, `unfeasible` and `documents_pending` have **no writer** in `covera-hono`. | Verified: `recomputeItemStatus` produces only `link_generated` / `photos_collected` / `complete`; nothing sets `escalated_to_aircover`, `resolved` or `unfeasible`; `documents_pending` is in the union with no transition into it. The UI **renders** these states correctly if they ever arrive and never offers a control that produces one. Blueprint row 5 (the 30-day vault) is therefore not built. | APPROVED |
| D16 | The status→tone/label mapping is one helper (`claimStatus.ts`), never a component comparing status strings. | The reservation section, the claim page and the field portal all render the same statuses; three string comparisons is how the same status ends up two colours. Same reason `proofWindow.ts` and `reservationActions.ts` exist. | APPROVED |
| D17 | The item-reissue control is shown **only** when `status === "link_generated"` and `tokenExpiresAt` is in the past. | `recomputeItemStatus` burns the token the moment status leaves `link_generated`, and `reissueToken` matches only `status = 'link_generated'`. A reissue button on any other status would call an endpoint that cannot succeed. For every other case the copy tells the host to add a fresh item. | APPROVED |
| D18 | The emergency banner is **sticky and red with a pulsing icon, but it does not flash**. | The blueprint says "sticky flashing red top banner". Flashing a large red region is a photosensitivity and vestibular hazard (WCAG 2.2.2), and it is the kind of thing that is much cheaper to decide now than to argue about in review. Sticky + saturated red + a pulsing `AlertTriangle` carries the same urgency. **Deliberate deviation from the blueprint — must be named in the PR.** | APPROVED |
| D19 | The ghost overlay is built as a **dimmed baseline still behind the capture preview** — no `getUserMedia`, no `<canvas>`, no MediaStream. | The data exists (`FieldIngest.baselinePhotos` is asset-scoped signed URLs from the most recent earlier stay, `[]` when there is none — verified in `getBaselinePhotos`), so the *feature* is buildable. What is not built is a live video pipeline: it needs a permissions flow, a stream lifecycle and a canvas compositor, and it would be the only `getUserMedia` call in the repo. The still gives the cleaner the framing reference the blueprint is actually asking for. | APPROVED |
| D20 | Photo capture reuses the repo's **`renderCamera` injection seam** and the native `<input type="file" capture="environment">` trigger. | `ShotStepPanel` already proves this pattern, including the part that matters for testing: jsdom implements no `URL.createObjectURL`, so the tests `vi.stubGlobal("URL", …)` exactly as `ShotStepPanel.camera.test.tsx` does. A second camera implementation would be the second thing to break. | APPROVED |
| D21 | Evidence types come from `FieldIngest.requiredEvidenceTypes` on the field portal, and from a **client-side helper** on the host side. | `getIncidentsById` returns `IncidentItem`, which carries no `requiredEvidenceTypes` field, so the host path must derive it. The helper pins the same three values as the backend's `PHOTO_EVIDENCE_FOR_TYPE`, and its test names that function as the source. **This is a duplicated backend rule; if `PHOTO_EVIDENCE_FOR_TYPE` changes, this helper must change with it** — it cannot be derived from the response. | APPROVED |
| D22 | The field portal's post-submit state is **local, with no navigation and no reload**. | The backend burns the token on submit, so a reload would show the "link unusable" screen immediately after success — the worst possible moment to tell a cleaner their work was lost. This is the blueprint's "Validation Block Screen". | APPROVED |
| D23 | The field portal's "link unusable" screen is **one screen for all three causes** (unknown, expired, already used). | The backend answers `404 FIELD_TOKEN_INVALID` for all three deliberately, to avoid being an oracle for token guessing. A UI that distinguished them would be re-deriving information the API refuses to give, and would do it wrongly. | APPROVED |
| D24 | The Airbnb deep link is a constant `AIRBNB_RESOLUTION_CENTER_URL = "https://www.airbnb.com/resolutions"`, opened in a new tab with `rel="noreferrer"`. | The blueprint asks for "a primary CTA action loop routing users to the specific external Airbnb Resolution interface". **I could not verify this URL from this environment** (no network probe of airbnb.com was made) — the URL must be confirmed by hand in the phase-7 browser pass, and it is one constant to change if it is wrong. | APPROVED |
| D25 | The claim message for the resolution-centre text box is built by a pure helper, `buildClaimMessage`, and copied with `navigator.clipboard.writeText`. | The clipboard path is the existing one (`GuestInspectionMessage`), and it needs the same `try/catch` + toast. Keeping the string construction in a pure helper makes the part that can be *wrong* testable without a DOM. | APPROVED |
| D26 | Adding items makes **one `postIncidentsByIdItems` call per asset** — never a batched `Promise.all`. | There is no bulk-add endpoint, and a `Promise.all` would make a mid-way failure leave an unpredictable set of items created with nothing able to say which. **Amended by D48:** the "behind one pending state" phrasing assumed one submit loops a multi-select; the form is single-asset, so each submission makes exactly one call and owns one pending state. The rule that matters — one call per asset, sequentially — is unchanged. | APPROVED |
| D27 | The asset picker lists the apartment's assets **minus those already on the claim**. | The backend refuses a duplicate with `INCIDENT_ITEM_EXISTS`; filtering first is what stops the UI offering an action the API will reject — the same principle as `getReservationActionAvailability`. | APPROVED |

## E. Process

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D37 | The regenerated `src/api/generated/requests/*.gen.ts` (4 modified files, currently uncommitted) are committed **by the operator, before phase 1**, as their own commit. | The incident surface is already regenerated in the working tree. Without committing it first, `git status --porcelain src/api/generated/` is non-empty for the whole feature and the "generated output is never hand-edited" invariant cannot be checked at any phase boundary. | APPROVED |
| D38 | The docs (`incident-claims.md`, `incident-claims.decisions.md`, `docs/incident-claims/`) are committed **by the operator**, separately from any code commit, before phase 1. | The precedent (inspection-guide D40), and the reason it exists: a code commit that also carries a thousand lines of plan text cannot be reviewed as a diff. | APPROVED |
| D39 | One commit per phase, made **by the operator**. The executor edits and runs the gate and **never commits**. | The operator's explicit instruction: "All the code additions from the steps should be commited by me, manually." | APPROVED |
| D40 | Phases land in numeric order, 1 → 9, with no parallelism. | Every phase ends with the same command on the same tree, and phases 5–9 all touch `host.json` or `guest.json`. Two executors on one tree produce a gate result neither can attribute. | APPROVED |
| D44 | The status-chip `TONE_CLASSES` map is **duplicated** into `ReservationIncidentSection` rather than hoisted into a shared module. | It is copied verbatim from `ReservationProofSection`, so the same tone is the same colour on the same page. Hoisting it would mean editing a component that has its own passing test in a phase that is otherwise purely additive, and it would couple two vocabularies (`ClaimTone` and `ProofStatusTone`) that have no reason to stay identical. A third copy is the point at which this reasoning stops holding and the map should be extracted. | APPROVED |
| D45 | A new i18n key is added in **the phase that first renders it**, not in the phase that names it. | A key named in an early phase and written in a later one is a raw key string on screen for the whole interval in between, and nothing catches it: `localeParity.test.ts` compares locale files to each other, not code to locales. So `incidentPage.status.*` lands in phase 5 (the reservation section renders the first status chip), `incidentPage.itemStatus.*` and `incidentPage.evidence.*` in phase 6 (the first item row renders the chip and the required-view list), the `incidentPage.*` filing keys in phase 8, and `fieldIncident.*` in phase 9. Each key-adding phase carries its own four-locale dump (D41). | APPROVED |
| D46 | The claim clock is read **once per page** and passed down as a `now: number` prop; no component below a page calls `Date.now()`. | `ReservationPage.tsx` already captures one `now` and hands it to the proof window, on the stated grounds that two `Date.now()` calls in one render are two answers to the same question. The reservation section and the claim page follow the same rule, which is also what makes both testable with an injected clock instead of fake timers (D32). | APPROVED |
| D47 | The tone→classes map becomes a new shared primitive, `src/components/shared/StatusChip.tsx`, in phase 6; the two existing copies (`ReservationProofSection`, `ReservationIncidentSection`) are **not** migrated. | D44 says the third copy is where the duplication stops being justified, and the item list is that third copy. Extracting it into a NEW file keeps phase 6 additive — no existing component is edited, so no existing test is touched — and the legacy maps are left alone because migrating them is a change to two components that each have a passing test. That migration is recorded in the spec's out-of-scope list rather than smuggled into this feature. | APPROVED |
| D48 | The add-item form is a **single-asset** form: one asset, one type, an optional value, one `addIncidentItem` call per submission, each submission carrying **its own** pending state. Adding five assets is five submissions. Not a multi-select. | D26 requires one `postIncidentsByIdItems` call per selected asset and there is no bulk endpoint. A single-asset form makes that call explicit and gives each item its own type — which matters, because the same asset cannot be both damaged and stolen, but two assets on one claim routinely differ. A `MultiSelect` would have to ask the type once for the whole selection, which is the wrong question. **Note:** this supersedes D26's "behind one pending state", which assumed a batched loop; D26's substantive rule — one call per asset, never `Promise.all` — still stands, and it is satisfied trivially when each submission adds one asset. | APPROVED |
| D49 | The add-item form sets react-hook-form's **`mode: "onChange"`**. | The submit is `disabled={… || !isValid}`, the `CreateAssetForm` pattern (`CreateAssetForm.tsx` line 295). Under react-hook-form's default `onSubmit` mode, `isValid` is only recomputed when a submit is attempted — and the disabled button is what prevents one — so the form would be permanently unsendable: a soft-lock the gate cannot see, because it type-checks and renders correctly. `mode: "onChange"` recomputes it as the host selects. The alternative (dropping `!isValid` from the disabled set) would let a submit through with no asset chosen and lean on the zod error, which is the worse of the two failures. | APPROVED |
| D50 | The field link's token is **session-only state on the claim page**. The page keeps a `Record<itemId, token>` seeded from the create and reissue responses; on a fresh page load there is **no token**, because `GET /incidents/{id}` answers with `IncidentItem`, which has no `cleanerToken` field — only `IncidentItemWithToken` (the create and reissue responses) carries it. With no token in hand the item card shows the link's **state** (`isItemLinkLive` / `canReissueItemLink` copy) and the copy control is absent. | Verified in `types.gen.ts`: `cleanerToken` exists on `IncidentItemWithToken` only. This is a backend contract, not an oversight here — but it means "show the cleaner's link" cannot be a pure function of the read, and a plan that assumed otherwise would have the executor inventing an endpoint or a query-key write. The add form therefore takes an optional `onItemAdded` callback (phase 6) purely to hand the created `IncidentItemWithToken` up; phase 7 owns the map. **Deliberate limitation to name in the PR:** after a reload the host cannot re-copy a link that is still live — they must wait for it to lapse and reissue (D17), or generate a fresh item. A persisted token would mean storing a credential in the browser for no security gain; the token is already single-use and 12-hour TTL'd. | APPROVED |
| D51 | `IncidentItemList` gains an **optional** `renderItemExtra?: (item: IncidentItem) => ReactNode` slot in phase 7, and the page passes the evidence and link components through it. | The index's phase-7 row lists the page and the two new components but not the list, so the naive shape would have the page render a second per-item pass beside the list — two loops over the same items, which is how the summary and the detail drift apart. A slot keeps one loop, keeps phase 6's render byte-identical when the prop is omitted (its tests pass unmodified), and keeps the list ignorant of evidence: it renders whatever the page hands it. The list is the composition point, not the owner of the evidence vocabulary. | APPROVED |
| D41 | Localisation of the i18n key inventory is per phase, in the phase file, as an exact `en` JSON block plus a per-locale `node -e` check. | The gate's parity check passes as long as the key exists in the other files — it does not check the *value*. Making the four-file write an explicit step, with a dump to prove it, is the only thing that catches a key written only into `en`. | APPROVED |
| D42 | No new `VITE_` variable; the Airbnb URL and the R2 image origin are constants and reused env respectively. | Everything `VITE_`-prefixed ships to the browser. This feature adds none. | APPROVED |
| D43 | `npm run build` is never used as an acceptance criterion in any phase, and `npm run perf:bundle` is used **once**, as an advisory check at the end of phase 3. | `npm run build`'s `prebuild` hook runs `api:generate`, which fetches `VITE_API_DOCS_URL` and rewrites the generated client — a gate that needs a backend is not a gate. The bundle check is advisory because it was measured while planning: the three new query resources and their SDK functions cost **+0.2 KiB** against a 92.0 KiB budget with the whole incident SDK surface already present (baseline `index-CvNgUDKZ.js` 90.4 KiB, measured 2026-11-08 at `e2fc012`). Phase 3 is the phase it belongs to: it is the only phase that adds to the entry chunk. | APPROVED |
| D52 | The confirm-filing success path **merges** the response into the cached entry; it never replaces it. `POST /incidents/{id}/confirm-airbnb-filing` answers with `Incident` (no `items`), while the cache entry is an `IncidentWithItems`. | Verified in `types.gen.ts`: `ConfirmAirbnbFilingResponses[200]` is `Incident`, not `IncidentWithItems`. A plain `setQueryData(incidentQueryKey(id), filed)` would blank `items` for at least one render and then restore them when the invalidation resolves — a flicker on the exact screen where the host has just filed a claim. The merge is `(previous) => previous ? { ...previous, ...filed } : previous`, so the write is still the source of truth for every field it carries. | APPROVED |
| D53 | Evidence deletion **is in scope**: the host can remove an evidence photo, via `DELETE /incidents/{id}/items/{itemId}/evidence/{evidenceId}`. The spec's out-of-scope line saying that endpoint "exists and is not called" is **superseded by this row** and the spec is corrected in place. | The two documents contradicted each other and the contradiction had to break one way. It breaks toward *calling* it, for three reasons: (1) a soft delete already exists server-side (`status: 'soft_deleted'` + `deletedAt`, and phase 1's `activeEvidence` already filters on exactly that pair, so the vocabulary was built for this); (2) the capture flow is the one place in the app where a user photographs a thing blind — a blurred or wrong-room shot with no delete is a dead end the host cannot recover from, and a bad photo attached to an Airbnb claim is worse than a missing one; (3) re-shooting alone does not help, because `MAX_EVIDENCE_PER_ITEM = 20` counts rows, not live rows — three bad photos and a 20-photo ceiling is a real limit. The out-of-scope line was written to stop the executor inventing a delete *UI* the plan had not specified; phase 7 specifies it, so the line's purpose is served by removing it. **Deviation to name in the PR.** | APPROVED |
| D54 | `FieldIngest.requiredEvidenceTypes` (`Array<string>`) is narrowed to the three photo types by a **type predicate** — `isFieldPhotoType`, derived from `FieldSubmitPhoto["evidenceType"]` — and never by a cast. | The union is needed for a `Record<FieldPhotoType, …>` label map and for the submit body, but `Array<string>` carries no union to narrow, so the three names have to be listed once. A predicate is the only form that both checks and narrows; a cast (`as FieldPhotoType`) would assert the shape and skip the filtering, and a `requiredEvidenceTypes` entry the portal cannot shoot would then be counted as required forever — the same soft-lock D49 records for the add-item form. Reusing phase 1's `requiredPhotoTypes` was rejected too: it is keyed off `IncidentItem["type"]` for the host surface, and this page already has the server's own answer (D21). Two copies of the rule on the page that needs it least is how they drift. | APPROVED |
| D55 | The `MAX_EVIDENCE_PER_ITEM = 20` ceiling **stays server-owned**. The field portal displays the counts the server sent (`attachedEvidenceCounts`) and does not re-implement the cap. | A client-side copy would be a second source for a backend constant with nothing keeping them equal — and the client would refuse photos the server would have accepted the moment the backend raises it. The failure it would prevent is a `400` whose sentence the screen already shows (D33), and a cleaner who can still send is better than a cleaner who cannot, on evidence they have already walked the apartment to collect. | APPROVED |
| D56 | The field portal sends **no coordinates**: `FieldSubmitBody.photos[].latitude`/`longitude` are omitted, and `capturedAt` comes from the file's own `lastModified`. | Reading coordinates needs a `navigator.geolocation` permission prompt, on a zero-auth page a cleaner opens from a link — no settings, no account, nobody to ask, and a denial is a dead end they cannot recover from. Nothing is lost by omitting them: the backend reads EXIF from the uploaded bytes itself, which is where the host panel's `exifLatitude`/`exifLongitude` come from. The timestamp is taken from the file rather than `Date.now()` at upload time, so a photo shot yesterday is not claimed as shot now (D46's rule: one clock, and the device's is the authoritative one here). | APPROVED |
