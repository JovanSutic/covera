# Purpose
the purpose of this file is to give information on how incident page and incident feature needs to be refined so it will have greater value for the user. This is the file where UX issues will be grouped and draft of the solutions as well. This file will be used as the main resource for next execution plan definition that will implement the fixes for these issues in the code.

# Issues
1. Photo number issue. At the moment the incident page is mirroring the photos that are needed in the inspection phase. So basically if the asset is flagged as close-up then we incident will define that we need a swipe and close up photos for it. This is partly right, because sometimes we would need even more photos to prove to the insurer that the damage really happened.
Fix - Have these mandatory photos but also have additional photos if the host feels like he would like to present the damage as best as possible. Single asset shouldn't have more than 4 incident photos in total. This should be checked on the BE side, if this is a possibility. But generally this should be the right UX. Adding mandatory photos and having the option to add additional photos, not more than 4 in total per asset in the claim.

2. Clickability of the photos. Once the photo is made it can be deleted or retaken, but it can't be click upon and seen in a bigger format. This is not the good UX, as the photos are proofs, we should enable the host to closely look at them.
Fix - allow user to click on the photo and with that click open a bigger version of it. We already have a component that we are using for this ExpandableImage. Maybe just extract the functionality of opening this larger format from this component and apply it on this smaller image in the incident page.

3. Before photos. In the Affected assets section, per asset we need to see the before photos. We need to show it there bellow or above the photos that are proving damage, and they need to have the same format as the photo of the damage but they can't have the delete button on them.

4. Price per asset. In the section What you are asking for, I need to have price per asset, like a list where we have asset 1 amount to request, the asset 2 amount to request. So basically this should mirror the assets, when ever we have and asset added to the claim we need to add the same in this section as well. It should be a line with a input on the end, in that input we can add the number, so there should be validation. Default number is 0, but also that number is invalid, amount should always be more then 0. So you add an asset, then in this section that same asset is added with some error indication on the input (border red probably) because the amount is 0. You can always change it until the claim was sent, the request was sent. After it is send this is not to be changed.

5. In the Request text we need to add some data about the apartment and the reservation and it should be light weight. Like Hi, you were out guest in Name of the apartment, from dates to dates. Unfortunatly there was a theft or a damage made during this stay. These are the assets that were being damaged/stolen: then the list of assets with the price.
And at the end some also light conclusion. Like we hope you will accept to pay to cover all this damage and not got through the more complex claim procedure, something like that. And we mention in the message that we will attach the photos of before and after state. So it should be light weight, if should mention the dates, the apartment, the assets and cost per each, total at the end and friendly ask to avoid the more complex procedure and mention that we have before and after photos that will be attached.

6. This should all be translatable, the whole page seems to be lacking the language translation. At the moment when I change the language on the incident page nothing is happening. We need to implement langauge translation for this page.

7. We need to add lang to the links inside of the system. So right now when you translate one page, like you are on the reservations page and you change the language to serbian it is changing that page, but then when you click on some link, you end up on a different page on with the default language. Meaning language is not persistant accross the pages. This needs to be fixed, somehow all my links need to know about my language and they need to add the lang= param automatically so I will always end up on the page with correct language.

8. There is a little part on the Affected assets, link shown when the item is added. I need an explanation what is this part really doing and why is it there, now there is no link just an icon and this text which is misleading and not really clear. What was the point and do we really need this here.

9. In the damage claim section on the reservations/:id page, we need to have some link that will lead the user to the page where this damage/theft claim is explained. How it is functioning, what he needs to do what are the important things he needs to know. Basically when you find the damaged asset you need to know what the procedure looks like. What do you need to do. Like collect the photos right away, provide some data about the costs, provide some documents about damage/repurchase/repair appraisal. What are the deadlines that needs to be met. How the whole process looks like on the Airbnb resolution center side etc. So we need to have a page where all of these data would be structered and presented, and on the damage claim section we need a link to it.

10. Damage claim section can be seen but the creation of the claim can not be possible before the checkout. So we need to wait for the checkout time and then the button for creating claim can be enabled.

11. In What are you asking for section. We need more elaboration for the cost. So there is something that is our imitiade reaction, and this is the damage asset request this is what I was talking about in the point 4, price per asset. But this needs to be developed a little bit more, basically we need a process where we will say this asset will be repaired, here is the document that is telling how much this repair will cost. Or the asset needs to be replaced, this is how much the new equivalent asset is worth. we need to add maybe some lost business, like we needed to cancel the reservation because of this damage. and all of these should be covered with some documents that are proving this. We should have max 2 uploads per this damage fix proposal. Like you ask for 500 for the TV and you choose repair and you provide 2 documents and some message that will explain why repair is the way to go. The same is for the repurchase, because the damage is beyond repair. etc. The whole point is to prepare everything for the claim, and to prove that you really need those funds, this should be checked with the BE if it is compatible and if it can be done.

# Result
The result that we want to achive with this execution plan that will come out of this file, and the code that will come out of that execution plan is more security for the host. He should know the procedure, he chould know what his imidiate response should be, where he needs to channel the energy, the app should provide him the slots to document everything that is needed in the damage claim process and it should offer an easy to use UI for management of this procedure.
