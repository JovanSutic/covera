## A. Prep §1 — the strip's active ring

| Id | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D1 | `StripItem` gains exactly one field, `isActive: boolean`. It is `isCaptured(shot) && index === viewedIndex && index !== cursorIndex` — the captured step the host has **tapped into**, and only while the cursor is elsewhere. | The operator's three rules collapse to one predicate plus `isCurrent`: current-wins is handled in markup by ordering, not by a fourth field. **Corrected 2026-11-01 — the first draft was `isCaptured(shot) && index !== cursorIndex`, which lights up _every_ finished photo at once** (fact 17). That is the opposite of a "you are here" ring, and prep §1's own words settle it: "the user will click on the item that was already done and has the photo, and he will be moved to that step ... The step is not somehow highlighted." The `isCaptured` guard is redundant on the path the flow takes (`selectStep` refuses to move the view onto a pending step) and is kept anyway, because invariant 10 says this module owns the decision — a pending item renders no button, so a ring on one would be both unreachable and wrong. | APPROVED |
| D1b | The third parameter of `inspectionGuideSteps` is `viewedIndex`, from which D1 reads `isActive`. It is a **parameter of the helper**, not a prop on `PhotoStrip`. | D1 needs the viewed index and `PhotoStrip` must not be given it (R1). The flow already holds both indices as its own state, so passing both to the one function that answers "what does the strip look like" keeps a single source of truth — and keeps `PhotoStrip` and `PhotoStripItem` comparing nothing (invariant 8). | APPROVED |
| D2 | The class is `ring-2 ring-orange-400 ring-offset-1 dark:ring-offset-gray-900`, replacing the current ring when both apply. | `ring-2` on both and `currentRing` placed after `activeRing` in the template literal means the array order decides, and the emerald wins without an `if`. | APPROVED |
| D3 | The ring's *reserve* on the row: `p-1` on the scroller and `py-1` on the wrapper stay exactly as they are. The `✓` item needs no new reserve. | Measured on 2026-11-01: the current reserve is `4px (p-1) + 3px (ring-2 + ring-offset-1) = 7px` on every side, which fits the tallest possible icon-plus-label row inside the reserved height (69px used of 72px). The constraint is the row height, not the rings — see R3. | APPROVED |
| D4 | `stripItems` is **replaced** by `inspectionGuideSteps(shots, cursorIndex, viewedIndex)`. `PhotoStrip` gains a `photoCount` prop (D17c) and its `items` prop keeps its type and its meaning. | `PhotoStrip` calls the helper at `InspectionGuideFlow.tsx`, which holds both indices. ## D. Prep §4 — tooltip placement

| Id | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D23 | A new pure module `src/lib/helpers/tooltipPlacement.ts` exports `computeTooltipPlacement(input): TooltipPlacement`, where `input` is `{ trigger, host, panelWidth, panelHeight, preferred, gap }` — all plain numbers and rects, no DOM. | Operator chose "measured hook + clamping". The measurement is DOM; the placement *rule* is not, and the rule is the part worth testing. This is the repo's existing pattern (`proofWindow.ts`, `reservationActions.ts`). | APPROVED |
| D24 | The rule: place below the trigger by default (or above when `preferred` says so and there is room); choose `align` (`left`/`center`/`right`) so the panel's span sits inside `host`; when the panel is wider than `host`, set `align: "left"` and return `width = host.width`; then clamp `left` and `top` into `host`. `placeBelow` flips to `false` only when below overflows `host` and above does not. | These are the four sentences in prep §4 in order: fit inside, flip towards the space, never cross the wrapper, be smart about width and height. Every branch is a pure comparison, so every branch is a test case. | APPROVED |
| D25 | The measuring half is a hook, `src/hooks/useTooltipPlacement.ts`, returning `{ hostRef, triggerRef, panelRef, placement }`. It resolves the host by `triggerRef.current.closest('[data-tooltip-host]')`. | One ref for the host means a call site opts in by rendering inside `PageLayout` and nothing else; `closest` cannot cross to a sibling subtree, so a tooltip in a modal gets the viewport fallback (D28) rather than silently clamping to the page behind the modal. | APPROVED |
| D26 | The opt-in attribute is `data-tooltip-host`, carried on `PageLayout`'s `main` element (`src/components/layout/PageLayout.tsx`). | `main` is the only element every page has exactly one of, and `PageLayout` is what the prep names as the boundary. A tooltip outside `PageLayout` (there is none today) falls back per D28. | APPROVED |
| D27 | `InfoTooltip` renders its panel through `TooltipPanel`, a new component in the same file that owns the clamped position. | The panel is currently a `<span>` inside a `<span>` that is inside `ActionButton`'s `inline-flex` — an absolutely-positioned box with no ink on an inline formatting context. `TooltipPanel` puts `position: relative` on the wrapper so the measured panel ink is inside it, and hands the caller a plain `<div>` wrapper. | APPROVED |
| D28 | The viewport is the fallback host when no `[data-tooltip-host]` ancestor exists. | A tooltip inside `Modal` (which portals to `document.body`) has no `PageLayout` ancestor. | D29 | `InfoTooltip`'s markup is restructured: `div.relative` wrapper → `button` + `TooltipPanel div`. ## Rejected alternatives

| Id | Alternative | Why rejected |
| --- | --- | --- |
| R1 | A `viewedIndex` prop on `PhotoStrip`, so the item decides `isActive` itself. | Puts a second copy of "where the host is" in the render tree, and the helper module's whole purpose (its own header comment) is that it is the only place that answers that question. |
| R2 | Three ring classes emitted from the helper (`none` / `current` / `active`) instead of two booleans. | A class string in a pure helper is untestable in jsdom and unverifiable by grep; two booleans are both. |
| R3 | Give the `✓` item its own taller tile so the caption fits. | Measured: the reserved row is 72px and the tallest realistic tile is 69px. Spending a new reserve on a hypothetical taller tile would change the strip's height on every page for no observed defect. Recorded so it is not re-proposed — if a locale ever produces a 3-line caption, the fix is `truncate` on the tile, not a taller row. |
| R4 | Special-case `cursorIndex === shots.length` in the strip with a literal. | `shots.length + 1` appeared three times in the first draft. One function owns it (D17). |
| R5 | Keep the `shotGuide.review.checklist` paragraph and add the back link below it. | The checklist's job was "look at the list before submitting"; the list is now the way back to every photo, including the one just taken. Two competing instructions on the confirmation screen is worse than one. |
| R6 | Pass `shots` (and a `setShots`) into `GuideReviewScreen` so it can re-capture inline. | The page's mutation is bound to the flow's array by `onSubmit={() => onSubmit(shots)}`. A second editor of that array makes `cursorIndex === shots.length` unsound, which is the entire mechanism of prep §3. |
| R7 | Make the tooltip a `Popover`. | It portals to `document.body` at `z-9999` and would clash with the `Modal` layer `ReservationProofSection` sits in — the exact reason `InfoTooltip`'s own comment gives for not being one. |
| R8 | Clamp tooltips to the viewport instead of `PageLayout`. | The operator asked for the wrapper, and the repo's convention is linkable: the same complaint ("confined with the wrapper") is already recorded in `ReservationActionsBar`. |
| R9 | Delete unused exports as well as unused files (`parseDateTime`, `publicApi`, prop-type exports). | Operator-chosen scope. `publicApi` is additionally named in the repo's own invariant list as the app's public API surface — deleting it would contradict an invariant rather than tidy up. |
