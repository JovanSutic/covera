## Decisions

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D1 | Every resource gets a **query definition module** under `src/lib/api/queries/`: `apartment.ts` (exists), `assets.ts`, `shots.ts`, `reservations.ts`, `inspection.ts`, `admin.ts`. Each exports `xQueryKey(...)`, `fetchX(...)`, `useX(...)`. | The route's prefetch and the page's hook must not be able to drift. `apartment.ts` already proves the pattern and its test already asserts key/args identity. Making it universal turns "same key = same args" (§4, D37) from a convention into structure — and gives the coverage check (D12) a manifest to read. | APPROVED |
| D2 | A route declares its data dependencies as `data?: readonly QueryKeySpec[]`, a list of the declarative query descriptors it needs. `prefetch` **stays** for anything not expressible as a descriptor. | The builder must be able to *know* what a route fetches in order to check coverage. An opaque `prefetch` callback is unverifiable; a descriptor list is data. Keeping `prefetch` as an escape hatch avoids blocking a route that needs bespoke logic. | APPROVED |
| D3 | `prefetch` and `data` entries receive `(params, searchParams)`. `guard.preload` is called with `url.searchParams` from the href; `makeLoader` passes `new URL(request.url).searchParams`. | Tab state lives in the URL (`?tab=apartments`) and `Tabs` renders only the active tab, so a tab-scoped query is unreachable by params alone. Without this, `/admin/dashboard?tab=apartments` prefetches the wrong tab's data. | APPROVED |
| D4 | `buildPreload` no longer requires a page/layout module. It returns a preload when the node has *either* a module to import *or* `data`/`prefetch` to run; the import is skipped when there is no module. | This is hole 1. A group route (`hostRoutes`) has `prefetch` but no `page`, so `buildPreload` returned `undefined` and the section prefetch never ran on the intent path. | APPROVED |
| D5 | One exported constant `PREFETCH_STALE_TIME_MS = 30_000` in `src/lib/api/queries/shared.ts`, used by every prefetch **and** every corresponding `useX` hook. | Hole 4. Prefetches used 30 s while `queryClient` defaulted to 15 min, so after 30 s a hover refetched a query the page considered fresh. One constant used by both sides makes the mismatch impossible. The value stays 30 s (not 15 min) because a prefetch is speculative work that should not pin stale data on screen. | APPROVED |
| D6 | Register `APARTMENT_SHOTS_GET_BY_APARTMENT` in `QUERY_ACTIONS` and replace the two string literals in `IndividualApartment.tsx`. | Hole 2's prerequisite, and invariant 5 already forbids the literal. The shots query cannot be prefetched by a shared module while its key is an ad-hoc literal in a page. | APPROVED |
| D7 | `/inspection/:id`'s query moves to `src/lib/api/queries/inspection.ts`, and its `queryFn` calls `getInspectionsById({ path, query })` with **no** config spread — exactly as the page does today. It does **not** use `withAuth()`. | **Corrected after verification — the original "use `withAuth()`" was wrong and would have broken the guest flow.** The inspector URL is generated by a host (`ReservationActionsCell.tsx`) and shared as a copy-link message to a **guest with no session**, so the request must be anonymous. `withAuth()` would attach `Bearer undefined`. The rule that governs here is §4 — the prefetch must build the *same* request the page does — so the page's existing anonymous call is the specification. | APPROVED |
| D20 | The pre-existing base-URL split is **preserved, not fixed**: the four authenticated flows override `baseUrl` with `VITE_BASE_URL` (via `withAuth`), while `/inspection/:id` and `postInspectionsByIdFlags` rely on the generated singleton's hardcoded `https://covera-api.josutic-sutic.workers.dev`. This is recorded and reported, not changed. | They are two different hosts, and changing either is a backend-contract question outside this feature (D15). Unifying them could break the guest flow or the authenticated API, and is not needed to close the five holes. Flagged to the operator in the PR. | APPROVED |
| D8 | `/host/apartments/:id` prefetches **all four** of its queries: apartment, assets, shots, reservations (page 1, default sort). | Hole 2. Prefetching only the apartment leaves three mount-time requests after the chunk — the dominant waterfall. All four are unconditional on this page (`enabled: !!id`), so all four belong to the intent. | APPROVED |
| D9 | `/admin/dashboard` prefetches the **default tab's** data unconditionally, and the non-default tab's data only when `searchParams.get("tab")` names it. | Admin is hole 6 (nothing prefetched). Eagerly prefetching both tabs would waste a request for a tab the user may never open; conditioning on `?tab=` gets the benefit at no cost. | APPROVED |
| D10 | Delete the `recordCheck` capability: the `recordCheck?` field on `PageRoute`, and its `Promise.all` arm in `makeLoader`. | Declared, wired into the loader, defined by **no** route — dead capacity that the coverage work would otherwise have to reason about. Removing it is a deletion, not a redesign. | APPROVED |
| D11 | `NavigationTiming` gains `chunkMs` (today's number, renamed), `dataMs` (nav idle → last query started for that nav settled), and `prefetched` (was this href preloaded before the nav). `ProgressBar` is unchanged. | Hole 5. `getMedian()` today reports chunk time, so the baseline's `9.2 → 7.2 ms` cannot support any claim about data. `dataMs` is closed by subscribing to `queryClient.getQueryCache()` and waiting for the queries started since nav began. | APPROVED |
| D12 | A new gate check `src/lib/router/__checks__/prefetchCoverage.test.ts` statically scans each route's page module and its transitive local (`@/…`) imports for query-module registrations, and fails when the page reads a query the route does not declare. | This is the structural guarantee. It is a source-level check, so it needs no browser and no backend, and it fails at the exact step that introduces the regression. Exemptions are an explicit allowlist (D13), never silence. | APPROVED |
| D13 | The coverage check's exemption list starts with **one** entry: `Tabs` content for a **non-default** tab (`?tab=`-gated). Each exemption is a named entry with a one-line reason, and the list must be edited deliberately. | Hole 5 of the original review is the class of bug, not one instance. Tab-gated content is genuinely conditional, so it is the one honest exemption. An allowlist keeps it visible rather than letting the check be weakened globally. | APPROVED |
| D14 | Prefetches are always fire-and-forget: `void prefetchQuery(...)` wrapped in a helper in `src/lib/api/queries/shared.ts` that catches and swallows. | A prefetch must never break a navigation. `preloadRegistry.preloadRoute` already catches synchronously, but the promise rejects asynchronously — so the catch belongs at the call. | APPROVED |
| D15 | No route path, guard, access rule, component, or i18n key changes. The diff is prefetch coverage, router plumbing, timing, and one dead-code removal. | The feature's whole value is *when* requests start. Changing what renders would make the perf claim untestable and widen the review surface for nothing. | APPROVED |
| D16 | Phases 1, 2, 3, 4 and 5 each end with a test step. Phase 6 (baseline re-measure) has none — it produces numbers, not logic. | Phases 1–5 introduce a query module, router plumbing, route declarations, a check, and a timing recorder: all testable pure-ish logic, so the skill's test rule applies. Phase 6 is a measurement run whose acceptance is the recorded output. | APPROVED |
| D17 | One commit per phase; the docs commit is separate. | Repo convention (the prior feature's D49) and the skill's Stage 7 division of labour. This repo has no hooks and no CI, so the convention is the only record. | APPROVED |
| D18 | The entry-chunk budget (94,208 gzip) is **not** raised in this feature. If a step measures it exceeded, that is a halt-and-ask, not a silent bump. | Confirmed headroom is 3,642 bytes (90,566 / 94,208). The generated SDK is already in the entry chunk, so the marginal cost of these prefetches is expected to be small — but "expected" is what the budget exists to falsify. The operator selected raise-only-with-evidence. | APPROVED |
| D19 | `docs/routing-performance-baseline.md` is **recreated** (it was deleted in `0fa546c`) as part of phase 6, carrying the original tracker rows from git history plus the new `dataMs`/`prefetched` columns. | Definition of done requires the perf claim to be re-measured and recorded. Without the file there is nowhere to record it, and the previous numbers are only recoverable from history. | APPROVED |
| D21 | Phase 3 converts `ApartmentSection`, `UsersSection` and `ApartmentSections` (admin) **off inline `useQuery`** onto the phase-1 module hooks. Phase 4's check detects a query by the **named import** of a registered hook, so a component using an inline `useQuery` is invisible to it. | **Added after verification.** Without this the check passes *vacuously* on the two routes it most needs to cover: `hooksUsedBy(pages/host/ApartmentList)` returned `(none)` because `ApartmentSection`'s query is inline, so the host section's data would stay uncovered while the gate showed green — a check that proves nothing is worse than no check. Verified by running the walk against the real files. | APPROVED |
| D22 | Phase 4's test file asserts the **parser's own behaviour** (a default import is read; nine specifiers are found; the admin page's hooks are reached transitively through its default imports; the host detail page's set is exactly four) before it asserts coverage. | A regex that silently matches nothing makes every coverage assertion vacuous, and this plan's first parser draft had exactly two such bugs — a brace-only import regex that missed `import Tabs from …`, and a module-name match that credited a page with every hook its imported module exported. Both were caught by running the walk against the real tree. The parser guards are what make "0 gaps" mean something. | APPROVED |

## Checklist — close every one of these before approval

**Shape**
- [x] Route path, and which ecosystem it belongs to — **no route paths change** (D15). The routes
      touched are `host/*`, `admin/*`, `inspection/:id`; the first two are authenticated sections,
      the third is public.
- [x] Component location — no new components. New *modules* are data-only, at
      `src/lib/api/queries/<resource>.ts`.
- [x] Server state vs local state — unchanged: all of it stays in react-query. The only new state
      is `NavigationTiming`'s buffer, which is a dev-only module-level array, not React state.
- [x] `QUERY_ACTIONS` key — reuse the eight existing entries; **add one**,
      `APARTMENT_SHOTS_GET_BY_APARTMENT` (D6).

**API**
- [x] Generated request functions used, by name: `getApartmentsHostMe`, `getApartmentsById`,
      `getAssetsApartmentByApartmentId`, `getApartmentShotsApartmentByApartmentId`,
      `getReservationsApartmentByApartmentId`, `getInspectionsById`, `getUsers`, `getApartments`,
      `getLocations` — all verified present in `sdk.gen.ts`.
- [x] Does the backend already expose it? — **Yes, all of them.** No contract change, no blocked
      phase.
- [x] Does `npm run api:generate` need re-running? — **No.** `src/api/generated/` is untouched.
- [x] Auth: `withAuth()` for every authenticated query. **`/inspection/:id` is the deliberate
      exception and stays anonymous** (D7) — it is reached by a session-less guest via a shared
      copy-link. No `publicApi()` use is added: it is exported but called nowhere in the app, and
      D20 leaves the pre-existing origin split alone.

**Auth and routing**
- [x] Guard that runs — unchanged. `canOpenHost` / `canOpenAdmin` / `public`.
- [x] Every role that may reach each screen — host: `admin` and `host` (per `access.ts` rules);
      admin: `admin`; inspection: `public` (anonymous included).
- [x] Deliberately public — `/inspection/:id` is public by design (the guest-facing inspection
      flow, R… in `public.ts`). Unchanged.
- [x] Lazy-imported in `src/App.tsx` — n/a and deliberately so: invariant 4 was *replaced* by D5 of
      the router-maximization feature. Routes live in `src/lib/router/routes/*.ts`; `App.tsx` mounts
      the router only.

**States** — no new screens; each listed route's states are already handled. The feature changes
*when* data arrives, not which states exist.
- [x] Loading — every touched page already has a loading branch; unchanged.
- [x] Empty — `ApartmentSection` and the admin tables already render empty states; unchanged.
- [x] Error — `RouteError`/query error branches exist; unchanged. A prefetch failure deliberately
      does not surface as a route error (D14).
- [x] Success — unchanged.
- [x] Optimistic vs pessimistic — **n/a**: this feature adds no mutation. All touched mutations keep
      their existing invalidation.

**Copy and i18n**
- [x] Namespace — n/a: **no user-facing string is added or changed** (D15). No locale file is
      touched, so the four-locale invariant cannot be broken by this feature.
- [x] Key names — n/a.
- [x] Translated copy ready — n/a.

**Forms** — n/a: this feature has none.

**Evidence**
- [x] Testable logic in phases 1, 2, 3, 4, 5 → test step required and specified in each (D16).
- [x] Exemption — phase 6 only, with the one-line reason in D16.
- [x] Tests live beside the module: `src/lib/api/queries/*.test.ts`,
      `src/lib/router/defineRoutes.test.ts` (existing, extended),
      `src/lib/router/__checks__/prefetchCoverage.test.ts`,

**Process**

## Rejected alternatives

| ID | Alternative | Why rejected |
| --- | --- | --- |
| R1 | Keep `prefetch` as the only mechanism and add no `data` descriptor (i.e. point-fixes only). | Explicitly not what the operator chose. It leaves the coverage hole reopenable: nothing fails when the next page adds a `useQuery` and forgets the route. |
| R2 | Put every page's full query list in one central registry file mapping route pattern → keys. | Two hand-maintained lists that drift, which is the original bug's shape. Deriving the page side from the actual module graph (D12) means the check reads one source of truth. |
| R3 | Enforce coverage with a jsdom integration test that mounts each page and spies on the QueryClient. | Faithful but expensive and brittle: it needs mocks for the generated API, the supabase session, and i18n, per page — and it would fail for reasons unrelated to coverage. The static scan catches the same regression for a fraction of the cost. |
| R4 | Raise the entry-chunk budget to make room, pre-emptively. | The operator chose raise-only-with-evidence. Headroom is 3,642 bytes and the SDK is already bundled; a pre-emptive bump would destroy the budget's only function. |
| R5 | Prefetch on route *render* (a `useEffect` in the shell) instead of on intent. | That is strictly later than hover: it runs after the click. It would also re-request on every render unless carefully guarded, and it puts data concerns in a view component. |
| R6 | Make `ProgressBar` reflect query-loading state so the improvement is visible. | Out of scope by the operator's answer. It also conflates two signals: a navigation can be instant while a query is slow, and the bar's current meaning (R9, visible after 200 ms) is deliberate. |
| R7 | Move the whole route tree into `App.tsx` to simplify the coverage check. | Violates invariant 4 as replaced by D5 — routes are data files, and the R1/R34 lint lock enforces it. |
| R8 | Unify the two API base URLs while moving the inspection query (route everything through `withAuth`). | Rejected: it would change which host the guest inspection flow talks to. That is a backend-contract change with real breakage risk, it is not needed for any of the five holes, and it would make this feature's diff span concerns a reviewer cannot verify from the plan. Recorded as D20 and reported instead. |
| R9 | Leave `/inspection/:id` unprefetched and exempt it from the coverage check. | Rejected: it is the cheapest hole to close (one query, no auth complication) and hole 3 of the operator's report. Exempting the very route being fixed would defeat the check's purpose on day one. |
