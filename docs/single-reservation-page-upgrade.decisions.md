## Rejected alternatives

| ID | Alternative | Why rejected |
| --- | --- | --- |
| R1 | Widen the existing `ConfirmActionButton` with an icon+label trigger so it covers both the table and the page header. | Its confirmation state is already cramped: it renders the Yes/No pair plus an optional `confirmMessage` inside a `flex gap-1.5` row, and the table's menu gives it `w-64`. Adding a label-bearing trigger of a different size and variant makes it two components in one file, and it is the wrong axis: `ConfirmActionButton` varies by *confirmation*, `ActionButton` varies by *appearance*. Composition (a confirm-capable content component inside a look-owning shell) keeps each axis honest. |
| R2 | Hand-roll the buttons with `clsx` instead of `class-variance-authority`. | CVA is already a direct dependency and is the idiom the surrounding `Card`, `GradientContainer` and `ConfirmActionButton` code is written in. A hand-rolled variant map would be a second convention for the same job. |
| R3 | Put the `Section` heading inside each phase's page file rather than in `SectionCard`. | The three sections then repeat the same 4-class container and the same `Typography type="h3"` wrapper three times, which is the duplication the pass exists to remove. |
| R4 | Fetch the apartment for the header with a `useApartment(reservation.apartmentId)` call. | It would be a **new request on every reservation-page visit** for two strings, and a new resource for `prefetchCoverage.test.ts` to account for. `apartmentsHost` is already prefetched by the section route (D15). |
| R5 | Keep the proof section's lazy read and show the count only inside the dialog. | It fails the prep's §4 requirement that the section itself "hold … info about how many photos there are and when the last one was captured", and it leaves the host returning from the capture flow with an empty state (D8). |
| R6 | Pass a React element into `ActionButton` for its label instead of a `string`. | The label must reach `title` and the accessible name, which need a string. `string` also makes the "no hardcoded user-facing strings" invariant checkable by reading the call sites. |
| R7 | Move the table's actions into a `Drawer` or a bottom sheet on mobile. | Prep §1 leaves the popover alone ("this is fine") and asks only for its layout and duplication to be fixed. `Popover` already portals to `body` and repositions on resize and scroll, which is the hard part. |
| R8 | Add `prefetchCoverage`'s `INTERACTION_GATED_HOOKS` entry for `useInspection`, since it is now read eagerly but the route declares it. | It is not interaction-gated any more — D8 makes the declaration real. Adding an exemption would convert a correct declaration into a permanently unverified one. |
| R9 | Suppress the "photos are ready" toast and instead auto-open the dialog on return from the guide. | Prep §7's "when he is returned back … he needs to be able to see the photos right away" is about *availability*, and it explicitly wants the dialog opened by a deliberate click. Auto-opening a modal on navigation is also hostile to a returning host. |
| R10 | Regenerate the four locales by hand-writing the German/Turkish/Serbian strings. | Guessing translations for four strings is worse than the machine pass the repo already owns (D26), and it would drift from the script's behaviour on the next run. |
| R11 | Colour-code the page's action buttons by purpose — blue for the copy-message link, amber for take-proofs, rose for delete. | It is the previous design, and it is exactly what the prep asks to remove. Three colours on three buttons of identical shape reads as three priorities, and the host has no way to learn which is which; §3 asks for one colour and one shape with an info affordance for the difference. | 
| R12 | Give `ConfirmButton` a single colour for both confirm steps. | The two triggers are now visually identical (D31), so the confirm step is the only place left that says *which* action is being confirmed, and the inline cell already distinguished them. A rose create-inspection step next to a rose delete step would also contradict the semantics `ConfirmActionButton` already established. |
