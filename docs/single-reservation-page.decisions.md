# Single reservation page — decisions

Every choice the executor would otherwise make mid-flight. Approve the table in one pass, or edit it
in place; do not leave a row in `OPEN`.

**Status values:** `APPROVED` · `OPEN` (blocks execution) · `REJECTED` (kept for the record)

---

## Scope split

This feature spans **two repositories**. Phase 1 edits `covera-hono`; phases 2–6 edit `covera`.
There is a hard stop between them: the frontend cannot compile against `getReservationsById` until
the new backend route is **merged and deployed** and `npm run api:generate` has read the regenerated
document. This mirrors the existing `docs/asset-type-change/p3.md` precedent, which has the same
shape and the same hard stop.

## Decisions

| ID | Decision | Rationale | Status |
| --- | --- | --- | --- |
| D1 | **The reservation page is `/host/apartments/:id/reservations/:reservationId`**, nested under the apartment it belongs to. **"Nested" describes the URL, not the route tree:** the route is a *sibling* of `apartments/:id` inside the `host` section's `children`, with the full pattern written out. | Operator-approved. It mirrors the existing `/host/apartments/:id` hierarchy, and — decisively — it puts `apartmentId` **in the URL**. The router prefetches a route's data from URL params via `data: [{ resource, params }]` (`src/lib/router/defineRoutes.tsx`), so a route without `apartmentId` cannot declare the shots/assets it needs and the gate's coverage check (`prefetchCoverage.test.ts`) fails it. With both ids present the route declares its whole data surface statically and a cold load starts every request alongside the chunk. **The sibling placement is forced by the tree, not a preference:** a child route renders into its parent's `<Outlet />`, and `IndividualApartment.tsx` has no `<Outlet />` (`grep -rn "Outlet" src/` finds exactly one occurrence, in `Shell.tsx`) — so a child route would match the URL, run its loader, and render nothing, a blank screen that passes every gate check. Being a sibling also means the node declares **both** `id` and `reservationId` itself, since sibling routes inherit no params from each other (`tree.test.ts` compares the path definition's param keys against the built route's). | APPROVED |
| D2 | **The guide page is `/inspection-guide/:apartmentId/:reservationId`**, a **top-level entry in `appRoutes`**, not under the `host` section. | Operator-approved, and it is the point of the exercise: the `host` section carries `requires: "canOpenHost"` as a *section* rule (`src/lib/router/routes/host.ts`), which every child inherits. A guide page nested there could only ever be host-only without restructuring the section. Top level gives the route its own rule, so the future capability guard (D8) is a one-line change. `apartmentId` stays in the URL for the same prefetch reason as D1. | APPROVED |
| D3 | **`GET /reservations/{id}` is built in phase 1 of this plan**, not assumed. | Operator-approved. `reservations.route.ts` currently has list/create/update/delete only — there is **no** single-reservation read, and the list endpoint is paginated, so a direct link to an off-page reservation cannot be served from it. `reservationsService.getById` already exists and is already used by `apartmentGuard`, so this is a contract + handler addition, not new data modelling. | APPROVED |
| D4 | **The new endpoint responds with `ReservationWithInspection`**, which already exists in both repos. | It is the same schema the list endpoint returns (`PaginatedReservationsSchema` wraps `ReservationWithInspectionSchema`), so it already carries the nullable `inspection` the page needs to decide between "take proofs" and "show photos". No new schema, no regeneration surprise, and the frontend type `ReservationWithInspection` is already in `types.gen.ts`. | APPROVED |
| D5 | **The new endpoint's middleware is `[authGuard, rolesGuard(["admin", "host"])]`, and the handler enforces ownership itself** via `assertApartmentOwnership(db, reservation.apartmentId, { userId, role, allowAdmin: true })` after loading. | Enforced, not assumed. `apartmentGuard` was the first choice, but it resolves an unknown id by querying apartments and then falling back to the reservation — so a reservation that does not exist would surface as `APARTMENT_NOT_FOUND`, not `RESERVATION_NOT_FOUND`. Checking in the handler gives the correct 404 and still rejects a non-owner, and it matches the existing `createReservationRoute`, which already calls `assertApartmentOwnership` in the handler. Note: `PATCH`/`DELETE` on a reservation carry only `[authGuard, rolesGuard(["host"])]` and check no ownership — a pre-existing gap, recorded in facts below and deliberately **not** fixed here (out of scope). The new read does not inherit it. | APPROVED |
| D6 | **`QUERY_ACTIONS.RESERVATIONS_GET_ID: ["reservations", "getId"]` is a new registry entry**, and `reservationQueryKey(id)` is its only key builder. | `QUERY_ACTIONS` (`src/lib/api/queryKeys.ts`) has `RESERVATIONS_GET_BY_APARTMENT` but nothing for a single id; adding the literal at a call site would violate invariant 5 and `registry.test.ts`'s "every entry carries a registry action" assertion. The naming matches the existing `APARTMENTS_GET_ID` / `INSPECTION_GET_BY_ID` pairs. | APPROVED |
| D7 | **A new query module `src/lib/api/queries/reservation.ts` exports `useReservation`, `fetchReservation`, `reservationQueryKey` and `reservationResource`**, registered in `QUERY_RESOURCES` **and** added to the `MODULES` map in `queries/manifest.ts`. | `manifest.ts` builds `QUERY_HOOKS` by scanning its `MODULES` object and **throws at load** if a `useX` export does not resolve to a resource of the same name registered in `QUERY_RESOURCES`. Omitting either half fails the gate. The `ResourceDefinition` shape (`key` + `fetch`) is what lets the route prefetch the very key the page reads — §4's "same key = same args" rule. | APPROVED |
| D8 | **The guide page's guard is `requires: "canOpenHost"` for now**, written at top level so the capability guard replaces one line. | Operator-approved: *"this guard and the whole functionality of creating and sharing this link is out of the scope of this task, I just need to find a place where this would live but not causing the conflict on the access rights."* A capability guard (a `?openFor=` identifier, or a `canUseGuideToken` rule) would also have to open the three **write** calls the flow makes — presigned upload tokens, confirm, and the status patch — all of which require a bearer token today. That is a separate feature, and the prep's out-of-scope note says so. | APPROVED |
| D9 | **Proof-window arithmetic moves into one pure module, `src/lib/helpers/proofWindow.ts`**, exporting `getProofWindowState(reservation, now)`. | Today that arithmetic is inline in `ReservationActionsCell` (effective check-in, `proofWindowHours ?? 4`, the −window/+1h bounds, the too-early/too-late/flags). Three surfaces now need it — the table menu, the page's proof section, and the guide page's own precondition. Copying it three times is how the "can I take shots" answer drifts between the button that offers it and the page that refuses it. Pure, so it is the feature's main test target. | APPROVED |
| D10 | **Coverage photos are never prefetched.** The routes declare `{ resource: "inspection", params: () => null }`, and `useInspection` is gated with `enabled: expanded`. | The prep is explicit: *"These photos I do not want to be loaded with the page load."* Returning `null` from `params` is the registry's documented "this navigation does not need it" signal (`registry.ts`), so the resource counts as **declared** — satisfying `prefetchCoverage.test.ts` — while `resolveResource` returns `null` and starts no request. `enabled` then gates the actual read on the host opening the control. The alternative (`INTERACTION_GATED_HOOKS`) was rejected: it is keyed by hook name globally, so it would exempt `useInspection` for every page rather than this one. | APPROVED |
| D11 | **Photos render with the existing `src/components/guest/RoomPhotoItem.tsx`**, grouped by room, unmodified. | The prep requires exactly this reuse — *"The photos should look the same as they are looking on RoomPhotoItem... this component should be reused."* It takes `{ shot, onFlagShot?, isFlagDisabled }`; the reservation page passes `isFlagDisabled` to hide the flag affordance, since flagging is the guest's action. Grouping by `roomLocation` mirrors `RoomDetails`, without porting its guest navigation chrome. | APPROVED |
| D12 | **Alternative-date editing is a small form on the page** using `patchReservationsById`, with its zod schema in `src/lib/validations/reservationDates.ts`. | The prep asks to edit alternative dates, refuse once check-in has passed, and implies the same for after. The existing `CreateReservationForm` schema asserts the identical pair of rules (check-out strictly after check-in; alternatives future-dated), so the validator extracts that shape rather than re-inventing it. Editing in place beats a navigation: it is two fields on the section the host is already looking at. | APPROVED |
| D13 | **The table's action row is a kebab (`MoreVertical` + `EllipsisVertical` from `lucide-react`) opening the existing `Popover`**, holding the four current actions. | The prep names the kebab explicitly. `Popover` (`src/components/Popover.tsx`) already gives click-outside and Escape dismissal, and is already used for the "copy guest message" action in the current cell — so the menu needs no new primitive and the guest-message panel keeps its current markup. | APPROVED |
| D14 | **`DataTable` gains an optional `onRowClick?: (row: T) => void`**, and the guest-name cell renders an `AccessLink` to the reservation page. | The prep wants the whole row clickable, and `DataTable` has no such prop today. `onRowClick` is optional and additive, so the three existing callers (`admin/ApartmentsSection`, `admin/UsersSection`, `host/ApartmentSection`) are untouched. The `AccessLink` in the first cell is not decoration: it is what gives the row a real `<a>` for keyboard users, middle-click and hover-intent preloading; `onRowClick` alone cannot. The actions cell stops propagation so the kebab never triggers navigation. | APPROVED |
| D15 | **`ReservationsSection.tsx` is deleted; `src/components/host/ReservationsTable.tsx` replaces it**, owning the query, the columns and the row click. | The prep names the component and the encapsulation: *"create a component ReservationsTable which will extract this view from ReservationsSection and encapsulate the api call and the table."* Its one caller (`IndividualApartment.tsx`) updates its import in the same phase. Leaving a re-export shim would preserve a name the prep asks to retire. | APPROVED |
| D16 | **`ReservationActionsCell.tsx` is deleted; its four actions become `ReservationActionsMenu.tsx` (table) and `ReservationHeaderActions.tsx` (page header), both driven by one hook, `src/hooks/useReservationActions.ts`.** | The prep asks for the same options as a kebab in the table and as buttons on the page. Two renderings of one behaviour must not be two copies of the mutations, the disable rules and the tooltips. The hook owns the delete and create-inspection mutations, the invalidation, and the `getProofWindowState` call; each component owns only its own markup. **The hook lives in `src/hooks/`, not `src/lib/hooks/`** — corrected against the tree: `src/hooks/` already exists and holds `usePreloadRoute.ts` (imported by `src/components/router/AccessLink.tsx` as `@/hooks/usePreloadRoute`) and `supabase.ts`, while `src/lib/hooks/` does not exist. Creating a second hooks directory would split the convention for no gain. The `@/*` alias (`tsconfig.app.json`) covers both, so the import is `@/hooks/useReservationActions`. | APPROVED |
| D17 | **Deleting from the reservation page navigates back to `/host/apartments/:id`** after invalidating. | The page it is standing on no longer exists once the reservation is gone. The alternative — leaving the host on a dead page that renders an error — is worse than the navigation. `IndividualApartment` is the natural parent because `apartmentId` is already in the URL (D1). | APPROVED |
| D18 | **i18n namespace is `host` for all new copy; the guide page reuses `assets.shotGuide.*` and `assets.roomLocations.*` unchanged.** | The flow being extracted already renders through `useTranslation("assets")` inside `ShotsGuide.tsx` / `InlineCamera.tsx`, and those keys exist in all four locales today (verified). Re-namespacing them would be pure churn and would risk the locale-parity gap this repo has no check for. New keys land under a `reservationPage` and `inspectionGuidePage` sub-tree in `host.json`. | APPROVED |
| D19 | **Copy is written now, as the key names in each phase's step, and `npm run i18n:translate` runs at the end of each phase that adds keys.** | Silence is not a decision. Writing the English now means the phases carry exact keys and the executor never invents one. The translate script is network-dependent, so it is a per-phase step whose failure is a halt condition, not a silent skip. | APPROVED |
| D20 | **Tests: phase 2 (query key + prefetch-shared-cache), phase 3 (proof window + date validator), phase 1 (backend 200/403/404).** | The skill's test rule. These are the feature's only pure logic. Phases 4, 5 and 6 are presentational plus wiring and are **exempt** — see D21. | APPROVED |
| D21 | **Phases 4, 5, 6 are exempt from the per-phase test step.** | Extracting an existing flow into a page, composing existing components, and rendering a table are the cases the skill explicitly permits exempting: the phases that carry the genuine branch logic (window arithmetic, date rules) are phases 2 and 3, and each of those ends with its test. A jsdom render of the extracted `ApartmentShotGuide` would assert that markup exists, which the operator's own click-through covers better and which would rot on the next style change. | APPROVED |
| D22 | **Commit granularity: one commit per phase**, docs separate from code, made by the operator at the phase boundary. | The skill's division of labour. Neither repo's `covera` tree has a hook or CI, so nothing runs a check unless someone types it; `covera-hono` *does* have a husky pre-commit, which gives phase 1 a second automatic check. | APPROVED |
| D23 | **`IndividualApartment.tsx` loses the inspection modal, `selectedReservation`, `isInspectionModalOpen` and `submitInspectionMutation` in phase 6**, but keeps `useShots` (the studio still needs it). | Removing the flow is what makes the extraction real rather than a copy. `useShots` must stay — `ShotStudioModal` consumes `preparedShots`. Because the route already declares `shots`, its coverage entry is unaffected. `useReservations` stays too: the unmatched-assets banner reads the default page's data (its existing D8 note). **Phase 6, not phase 4:** the modal must not be deleted until the page that receives the flow exists, and that page is phase 6's step 6.1. Phase 4 only repoints `ReservationsTable`'s `onTakeProofs` prop; the handler and the modal stay until phase 6, so phase 4 leaves nothing reaching for a path that does not exist yet. | APPROVED |
| D24 | **No new `docs/` note is needed for the guide page's future guard**; D8 and D2 carry it. | The operator explicitly deferred the guard. A row in this table stating the placement rationale is the durable record; a speculative design doc for an unbuilt guard would be the "decide later" anti-pattern wearing a different hat. | APPROVED |

## Checklist — close every one of these before approval

**Shape**
- [x] Route paths: `/host/apartments/:id/reservations/:reservationId` (host ecosystem, nested under its apartment) and `/inspection-guide/:apartmentId/:reservationId` (top level, deliberately outside the `host` section). D1, D2.
- [x] Component location: `src/pages/host/ReservationPage.tsx` and `src/pages/InspectionGuidePage.tsx` (routable screens — the latter at `pages/` root because it is not host-section-scoped, matching `src/pages/InspectionPage.tsx`); `src/components/host/ReservationsTable.tsx`, `ReservationActionsMenu.tsx`, `ReservationHeaderActions.tsx`, `ReservationProofSection.tsx`, `ReservationTimeSection.tsx` (host-scoped pieces); `src/lib/helpers/proofWindow.ts` and `src/lib/validations/reservationDates.ts` (pure logic). D9, D12, D15, D16.
- [x] Server state vs local state: react-query owns the reservation, the reservations list and the lazy inspection. `useState` owns only the photo panel's open/closed flag and the date form's edit/save state. No server data is mirrored into `useState`.
- [x] `QUERY_ACTIONS` key: **add** `RESERVATIONS_GET_ID`. Everything else reuses an existing entry. D6.

**API**
- [x] Request functions by name: `getReservationsById` (**new**, phase 2), `getInspectionsById` (via `useInspection`), `getApartmentShotsApartmentByApartmentId` (via `useShots`), `patchReservationsById`, `deleteReservationsById`, `postInspections`, and `submitInspectionPhotos` unchanged.
- [x] Backend exposure: **`GET /reservations/{id}` does not exist.** Phase 1 builds it. D3.
- [x] `npm run api:generate` **is** required, after the phase-1 deployment and before any phase-2+ step naming `getReservationsById`. It needs a reachable backend (`VITE_API_DOCS_URL`), which is why the hard stop exists.
- [x] Auth: `withAuth()` for every call. The one deliberate exception is unchanged and untouched: `fetchInspection` stays anonymous because `/inspection/:id` is the guest's shared link (its own D7).

**Auth and routing**
- [x] Guards: `canOpenHost` on the reservation page and (for now) on the guide page. Both are inherited-or-declared `RuleName`s used through `defineRoutes`, not `requireRoleGuard` — that function no longer exists in this repo; the router moved to rule names in `src/lib/router/access.ts`.
- [x] Roles that may reach the screens: `host`, plus `admin` where `canOpenHost` passes. No guest.
- [x] Deliberately public: nothing new. The guide page is **not** public (D8).
- [x] Lazy-imported: both pages are `page: () => import(...)` entries in route data files — `src/lib/router/routes/host.ts` (reservation) and `src/lib/router/routes/public.ts` (`appRoutes`, guide). Not `src/App.tsx`: this repo's router builds from route data and `App.tsx` only assembles the trees.

**States** — one row per state
- [x] Reservation page loading: the existing `PageSkeleton` per-route fallback, plus the sections' own skeletons.
- [x] Not-found: a reservation id that resolves to nothing renders the `PageTitle` not-found branch, matching `IndividualApartment.tsx`'s existing pattern.
- [x] Error: a rose-bordered panel with the message, matching `ReservationsSection`'s current error block.
- [x] Empty (photos): a reservation covered but with no active images renders an empty-state line, distinct from loading.
- [x] Empty (window closed / already covered) on the guide page: an explicit refusal state, not a silent redirect.
- [x] Success: sections render; mutations toast and invalidate.
- [x] Pessimistic on every mutation (no optimistic updates). Invalidation: delete → invalidates the apartment's reservations list and removes the reservation's own cache entry, then navigates; PATCH dates → invalidates the reservation entry and the list; create inspection → invalidates both; submit proofs → invalidates the reservation entry and the list.

**Copy and i18n**

## Rejected alternatives

| ID | Alternative | Why rejected |
| --- | --- | --- |
| R1 | `/host/reservations/:id` — the path the prep literally asks for. | It omits `apartmentId`, so the route cannot declare the shots/assets the guide needs, and a cold load serialises: reservation resolves → `apartmentId` known → shots fetch. That is the waterfall this router's prefetch machinery exists to remove, and `prefetchCoverage.test.ts` would fail the page. The operator chose the nested form. |
| R2 | Put the guide page under the `host` section so it inherits its guard. | The section's `requires` is inherited by construction in `defineRoutes`, which is exactly the conflict the operator wants avoided: a future non-host would be denied by the *ancestor* before the page's own rule is ever consulted. Top level is the whole point. |
| R3 | Make the guide page `requires: "public"` with the UUID as the capability, mirroring `/inspection/:id`. | It reads as the natural mirror, but the guide **writes**: presigned upload tokens, photo confirm, and the reservation status patch. All three need a bearer token. Opening them is the access-granting feature the operator deferred, and a public route whose primary action is a guaranteed 401 is worse than a host-only route. |
| R4 | Serve the reservation from the existing paginated list response. | Removes phase 1, but breaks on exactly the case the page exists for: a direct link, a bookmark, or any reservation not on the currently-loaded page. It also cannot express "reservation not found" — the page would show "no data" for a deleted record. |
| R5 | Add `useInspection` to `INTERACTION_GATED_HOOKS` instead of declaring `params: () => null`. | That map is keyed by hook name globally (`coverage.ts`), so it exempts the hook for **every** page rather than gating it on this one. It would also silently weaken the check for the page that genuinely needs the detailed read. D10 keeps the declaration local and visible. |
| R6 | A separate `GET /reservations/{id}/guide` returning reservation + shots + assets, so the guide URL needs only `reservationId`. | Genuinely the better end state for the future share link — minimal URL, one request. Rejected **for this task only**, by the operator, on cost grounds: it is a second new endpoint plus a hand-written resource, and today's guard does not need the short URL. Worth revisiting when the capability guard is built. |
| R7 | Keep `ReservationsSection` as a re-export of `ReservationsTable`. | Preserves a name the prep asks to retire and leaves two names for one thing, so the next reader cannot tell which is live. The one caller is updated in the same phase. |
| R8 | Put the proof-window state back into a `ReservationRow`-shaped type as a derived field. | `ReservationRow` (in `src/types/component.types.ts`) is a component-level view type whose `inspection` field is optional and whose shape already predates the `ReservationWithInspection` generated type. Extending it further entrenches a hand-written duplicate of a generated type. The pure helper takes the generated shape instead. |
