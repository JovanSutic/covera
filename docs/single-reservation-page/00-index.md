## ⚠️ The hard stop between phase 1 and phase 2

Phase 1 changes `covera-hono`. Phase 2 cannot compile until the frontend's generated client contains
`getReservationsById`, and that client is regenerated by `npm run api:generate`, which reads
`VITE_API_DOCS_URL` — the **deployed** OpenAPI document. So:

1. Complete phase 1, gate it, commit it, open and **merge** the `covera-hono` PR.
2. **Deploy `covera-hono`.** Until it is live, the document the generator reads has no new route.
3. Run `npm run api:generate` in `covera` and confirm step 2.1's Accept (the symbol exists).
4. Only then start phase 2.

Doing step 3 before step 2 produces a client with no `getReservationsById` and a phase 2 that cannot
typecheck. This is the same hazard `docs/asset-type-change/00-index.md` records for its phase 3, and
the same hard stop applies.

## Dependency rules

- A legal landing order: **1 → (deploy) → 2 → 3 → 4 → 5 → 6**.
- Do not start phase 2 before phase 1 is **deployed**, not merely merged — see above.
- Do not start phase 4 before phase 2 — the table's row click needs `appPaths.hostReservation` to
  exist, and phase 4 must not introduce it. Phase 2 owns every path definition and route entry.
- Do not start phase 5 before phase 3 — the proof section renders `getProofWindowState`, and the time
  section imports the date validator.
- Do not start phase 6 before phase 5 — the reservation page's "take proofs" action is the guide
  page's inbound link, and step 6.2 deletes the dialog that phase 5 replaced.
- Inside phase 4, the `DataTable` prop lands before the table that passes it (steps 4.1 → 4.4), and
  the deletes (4.5, 4.6) come last so the tree compiles at every step boundary. **Phase 4 must not
  reference `appPaths.inspectionGuide`** — that path is phase 5's (step 5.5), and a forward reference
  into it would put a red `tsc` at the end of phase 4. The shared action hook therefore does not own the
  guide URL; the phase that declares the path is the phase whose page builds it. This is a decision,
  not a preference (see D16).
- Inside phase 5, the page replaces the placeholder phase 2 created. **Phase 5 touches no router file
  for the reservation route** — phase 2 already landed that path definition, its route entry and the
  placeholder, because `tree.test.ts` fails a path definition with no route, which forces both halves
  into one phase.
- **Phase 5 step 5.5 lands the guide path, its route and a placeholder page, together.** Same rule,
  different entry: `tree.test.ts` fails a path with no route, and `coverage.ts`'s `resolveAlias`
  **throws** for a route whose `page:` specifier does not resolve. That makes the three an indivisible
  unit, and it belongs to phase 5 because phase 5's page is what links to the guide. Phase 6 therefore
  touches no router file either — it replaces a placeholder.
- Inside phase 6, the page (6.1) precedes the dialog removal (6.2): the removal must not happen until
  the page that receives the flow exists. Step 6.2 is a single edit because `noUnusedLocals` turns
  every orphaned binding into a red gate, so a partial removal does not compile.
- `paths.ts` is touched by phases 2 and 5, and `routes/host.ts` by phase 2 alone; `routes/public.ts` by
  phase 5 alone. Each touch adds a different entry, so the phases are order-dependent but not
  conflicting. `tree.test.ts` fails on a path definition with no route, which is why each phase lands
  its path and route halves together.

## Invariants — check at every phase boundary

1. `src/api/generated/` is not hand-edited; regenerate with `npm run api:generate` instead.
2. No hardcoded user-facing strings — every key exists in `en`, `de`, `tr`, and `sr-Latn`.
3. No secret in a `VITE_` env var; everything so prefixed ships to the browser.
4. Routes live in `src/lib/router/routes/*.ts` as `page: () => import(...)` entries built by
   `defineRoutes`; every authenticated branch carries a rule name from `ACCESS_RULES`. (The skill
   says `src/App.tsx` / `requireRoleGuard` — that is stale for this repo; see the facts table in the
   decisions file.)
5. Query keys come from `QUERY_ACTIONS`; no string literals at `useQuery` / `invalidateQueries` sites.
6. Network calls go through `withAuth()` / `publicApi()`. The one anonymous call
   (`fetchInspection`) stays anonymous.
7. Mutations invalidate the keys they changed.
8. Forms validate with a zod schema resolved through `@hookform/resolvers`.
9. **Feature-specific: `getProofWindowState` is the only computation of "can this host take shots".**
   No phase re-derives the window arithmetic inline. If a phase needs a variant of the answer, it
   extends the helper and its test — it does not copy the maths.
10. **Feature-specific: a route `data:` entry is declared for every query hook a page reads**,
    including the lazy one, which declares `params: () => null` (D10). `prefetchCoverage.test.ts`
    enforces this; a new page with an undeclared hook is a red gate.
11. **Feature-specific: no new i18n namespace.** New copy goes in `host`; `assets.shotGuide.*` and
    `assets.roomLocations.*` are reused unchanged.
12. **Feature-specific: the guide page's route stays at top level in `appRoutes` with its own
    `requires`.** It must not be moved under the `host` section, which would make the future
    capability guard (D8) impossible without restructuring the section.

### Division of labour

- **Executor:** edits, runs `npm run gate` per step, never commits.
- **Operator:** runs the gate at each phase boundary, makes **one commit per phase**, and owns the
  phase-1 merge + deploy that phase 2 depends on. In `covera` nothing enforces this — no hook, no CI
  — so the gate is the only thing catching a regression. In `covera-hono` the husky `pre-commit`
  gives phase 1 a second automatic check, but run the gate per step anyway so a failure is attributed
  to the step that caused it.
- Clear context at phase boundaries, not mid-phase.
- Tier the model per step: cheap for transcription, strong for phase 3 (the window arithmetic and the
  date rules are the reasoning-heavy steps) and for review.

## Known deviation from the skill

Phases 5 and 6 are large: phase 5 writes a page plus four components, phase 6 a page. They are kept
whole because each is **one user-visible thing** — a half-built reservation page is not a smaller
feature, it is a broken one — and because the alternative splits a page from the sections it composes,
which would put a red gate at the boundary for a reason no step in the split phase could fix. Both stay
under the skill's ~400-line target by carrying the *decisions* rather than restating the whole of each
file; where a step's Do is large it is because the file is new and there is no existing code to point
at. Phase 4 is a deletion phase and is deliberately narrow: its whole risk is leaving an unresolved
import. Phase 5 carries the guide route because `tree.test.ts` and `coverage.ts` together make a path,
its route and its page module indivisible — that is a structural constraint, not padding.
